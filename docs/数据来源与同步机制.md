# 数据来源与同步机制说明

> 更新日期：2026-08-31　|　适用版本：`38458de`（eloboard 新版 JSON API 迁移）

## 1. 背景

eloboard.com 于 2026-08 改版：**旧版 HTML 选手主页（`/men/bbs/board.php?bo_table=bj_list&wr_id=…`）全部 302 跳转到首页**，原 HTML 解析抓取永久失效。网站改为前后端分离架构（Next.js 前端 + JSON API 后端）。

改版期间同步曾出现"假成功"：脚本正常跑完、日志显示 46/46 成功，但解析到的是首页 HTML（无比赛数据），防回退逻辑保留了本地旧值，导致数据停更。本次迁移彻底切换到新版 JSON API。

## 2. 数据从哪里来（API 端点）

所有数据来自 eloboard 官方公开 API（与官网前端页面同源）：

| 端点 | 用途 | 说明 |
|---|---|---|
| `GET /api/players/{id}` | 选手详情 | 种族 `main_race`（T/Z/P）、当前 ELO `elo_raw`、头像 `thumb_url`、最近比赛日 `last_played_on` |
| `GET /api/matches?player_id={id}&limit=200&offset={n}` | 比赛列表 | 分页，最新在前；单页上限 200，实测深度 2000+ 场（可回到 2025 年前） |
| `GET /api/players?limit=200&offset={n}` | 全量选手枚举 | 共 1258 人（men=213 / women=1045），用于构建 ID 映射 |

**API 返回的比赛记录结构（单局粒度）：**

```json
{
  "id": 2112180,
  "played_on": "2026-08-26",          // 比赛日期
  "map_name": "옥타곤",                // 地图（韩文）
  "event_name": "ASL 시즌 22",        // 赛事名
  "round_label": "24강",              // 轮次
  "category": "solo_event",           // solo_event / pro_league / sponsored / team_event
  "format_raw": "단판",                // 赛制：단판=单局，"3/2(1)"=Bo3第1局，"7/4(5)"=Bo7第5局
  "elo_delta": 13.8,                  // 胜方 ELO 增益（恒为正数，败方为对称负值；部分赛事局为 null）
  "memo": "…",                        // 备注（同旧站 HTML 备注列）
  "participants": [                   // 参赛双方（顺序不固定！按 player_id 找本人）
    { "player_id": 39, "name": "김정우", "race": "Z", "result": "win" },
    { "player_id": 34, "name": "변현제", "race": "P", "result": "loss" }
  ]
}
```

关键语义：
- **Bo3 是 3 条记录**（`3/2(1)`、`3/2(2)`、`3/2(3)`），与旧站 HTML 的赛制标注完全一致，可无缝对账去重。
- **`elo_delta` 恒为胜方正增益**（如 13.8），本地转为本人视角带符号字符串（胜 `+13.8` / 负 `-13.8`）。
- **头像基址是 `https://eloboard.co.kr/static/`**（注意域名 `.co.kr`），拼接 `thumb_url`（如 `players/34.jpg?v=…`）。
- 当前 ELO 取 **`elo_raw`**（如 `1223.9`），`elo` 字段是档位值（如 `"1500.00"`），勿用。
- feed 端点 `GET /api/matches` **不带 `player_id` 时默认返回 women 部门**；men 需加 `division=men`。

## 3. 如何绕过 Cloudflare 反爬（抓取通道）

API 有 Cloudflare 盾保护，服务器和纯 HTTP 客户端直连会被拦。方案（`local-sync.js`）：

1. 本地电脑启动**专用 Chrome 实例**（独立 profile `.sync-chrome/`，窗口移出屏幕 + 任务栏隐藏），开启远程调试端口 `--remote-debugging-port=9222`。
2. 用 patchright（Playwright 分支）通过 **CDP 附着**该 Chrome，先访问一次 `https://eloboard.com/men` 激活/等待过盾（盾页标题多语言检测：Just a moment… / 잠시만… / 请稍候…）。
3. 过盾后用 **`context.request.get(url)`** 直接调 API——请求自带浏览器的 `cf_clearance` cookie，**无需打开页面**（JSON 请求比旧 HTML 方式快一个量级）。
4. 过盾 cookie 持久化在 `.sync-chrome/` profile 中，同步结束自动关闭 Chrome，不影响日常浏览器。

## 4. 旧 ID → 新 ID 映射

改版后选手 ID 体系变化（60 名跟踪选手中 34 个 ID 有变，如 변현제 34→33、방태수 178→151）。

- 映射文件：`data/player-id-map.json`（运行时数据，不入 git）
- 构建方式：全量枚举新站 1258 名选手，按**韩文名**匹配 `docs/韩国选手个人主页列表.md`（同名取 `games` 最多者），实测 60/60 全部匹配
- 重建命令：`node local-sync.js --rebuild-id-map`（MD 列表变动后运行；**映射文件缺失时同步前会自动重建**）

**对手 ID 落库规则**（保持与既有数据兼容）：
- 对手是 60 名跟踪选手 → 存**旧 wrId**（H2H 对战、跨选手去重与历史数据对齐）
- 对手是非跟踪选手 → 存 `'n' + 新id`（前缀 `n` 避免与旧 wrId 数字空间冲突）

## 5. 数据处理流水线（`db.js`）

```
API JSON ──转换──> 本地记录格式 ──增量合并──> data/players/{wrId}.json ──上传──> 服务器
```

### 5.1 字段转换（`convertApiMatch`）

| API 字段 | 本地字段 | 转换逻辑 |
|---|---|---|
| `played_on` | `date` | 直存（YYYY-MM-DD） |
| `participants` 对方 `player_id` | `oppWrId` | 经 ID 映射（见上节） |
| `participants` 对方 `race` | `oppRace` | T/Z/P 单字母 |
| `map_name` | `mapKr` / `mapCn` / `isSeasonMap` | 与 `public/maps.json` 赛季地图表匹配 |
| `participants` 本人 `result` | `isWin` | `win` → true |
| `elo_delta` | `eloChange` | 本人胜 `+X.X`，本人负 `-X.X`（绝对值） |
| `format_raw` | `format` | 直存（与旧站格式一致） |
| `memo`（空则 `event_name round_label`） | `memo` | 直存 |

### 5.2 增量合并与去重（`mergePlayerData`）

每次同步拉取 **120 天窗口**（UI 需 90 天，留余量）的比赛。合并语义：**本地库只增不减**。

- **常规同步**（本地已是 `source: 'api'`）：按去重键
  `date | oppWrId | map | format | W/L`
  逐条对账——API 上还有的由 API 版本替代，API 上没有的保留为历史；同键多条按数量对账（同日同对手同图多场不误删，如 멸망전 连续局）。
- **迁移同步**（本地是旧 HTML 数据，首次切 API）：两套 ID 体系无法逐条对账，采用**窗口整体替换**——API 窗口内的旧记录丢弃（API 是更深的超集），早于 API 窗口的历史保留。合并后标记 `source: 'api'`，之后走常规对账。
- **防回退保护**：API 异常返回空字段时保留本地已有值（race / elo / avatar / storyByOpp / mapStats）。

### 5.3 生涯统计的延续（两处特殊处理）

旧站 HTML 独有的两块生涯数据，迁移时经防回退逻辑**冻结保留为基线**，新数据在其上增量延续：

1. **生涯地图统计（맵별통계，按地图×对种族的生涯胜负）**：每名选手保留旧全量表作为基线；每次同步把**新入库的比赛**（API 自带对手种族，仅赛季地图）累加进对应地图/种族格。`mapStatsCutoff` 字段记录已累计到的最新比赛日期，防止重复累计。
2. **生涯互对战（storyByOpp，vs 每个对手的全量历史）**：旧站数据冻结保留；H2H 查询时由 `storyByOpp`（生涯）+ 双方 `matches`（持续新增）按键去重合并，生涯总分保持连续。

## 6. 日常运行流程

```
Windows 计划任务（每日）
  └─ run-sync-hidden.vbs（无窗口，单行裸代码——勿加注释，中文注释会使 wscript 静默失败）
       └─ run-sync.bat → node local-sync.js >> sync-local.log
            ├─ 自动启动/附着专用 Chrome（CDP 9222）
            ├─ 访问首页过盾激活会话
            ├─ ID 映射缺失时自动重建
            ├─ 增量同步：近 14 天有比赛的活跃选手
            │   （距上次全量超 7 天自动转全量，兜底"复活"的休眠选手）
            ├─ 下载选手头像到 data/avatars/（eloboard 外链被 Cloudflare 拦，必须本地化）
            └─ 打包上传：POST /api/upload-data（Bearer token，含 60 人数据 + 头像 base64）
                 └─ 服务器原子写入 data/players/、data/avatars/，经 /avatars 静态提供
```

常用命令：

```bash
node local-sync.js                # 增量同步（默认）
node local-sync.js --full         # 强制全量
node local-sync.js 12 34          # 只同步指定 wrId（测试）
node local-sync.js --rebuild-id-map  # 重建 ID 映射
node local-sync.js --upload-only  # 跳过抓取直接推送本地数据
node local-sync.js --no-upload    # 只同步不上传
```

## 7. 性能与校验

- **全量同步 60 人约 5 分钟**（旧 HTML 方式需 30+ 分钟；API 无需等待页面渲染）。
- **校验工具** `verify-migration.js`：对比每名选手本地最新比赛日期与官方 `last_played_on`，迁移当日验证 60/60 完全一致；含重复键检查、storyByOpp/mapStats 保留检查、H2H 与地图统计抽查。
- **成功判据**：`sync-local.log` 中的 `=====` 时间戳头（Windows 计划任务的 Last Result 不可信）。
- 迁移前旧数据备份于 `data/players-backup-20260831/`（旧 HTML 数据源已永久消失，无法重新抓取）。

## 8. 已知边界

- 官网首页"最近录入"feed 会显示**待确认的比赛**（如某日录入但选手页/API 尚无此局），此类数据待官方确认后才会被每日同步抓到——属正常现象，不是同步故障。
- 旧 feed 端点不带参数默认返回 women 部门数据；本工具按 `player_id` 逐人查询，不受影响。
- 部分赛事局 `elo_delta` 为 null（如职业联赛个别场次），本地对应 `eloChange` 为空字符串，前端显示为空。
